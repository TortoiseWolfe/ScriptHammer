What it is

A template you're allowed to take

ScriptHammer is a production Next.js 15 template. Not a starter you throw away at week two — the thing my own client sites run on.

What comes in the box

  • Next.js 15 · React 19 · TypeScript strict
  • Supabase auth, database, realtime
  • PWA, offline, service worker
  • 35 themes, WCAG-tested

What's unusual

  • 4,750 unit tests across 448 files
  • E2E on 3 browsers, per-runner Supabase
  • 7 checks must be green to merge
  • Docker-first — no "works on my machine"

The honest part

Templates usually rot at the seam

You take a starter, it fits for a month, then upstream moves and you're maintaining a fork nobody can merge into.

So the interesting question isn't "does it look good on day one." It's what does it look like ten weeks later, in production, owned by someone who isn't me.

Which is lucky, because that experiment already ran.

While it builds

A fresh fork has no secrets. It deploys anyway.

# every NEXT_PUBLIC_* deliberately empty — the fresh-fork condition
$ NEXT_PUBLIC_SUPABASE_URL= NEXT_PUBLIC_SUPABASE_ANON_KEY= pnpm build
✓ 140 pages built
BUILD EXIT: 0

You get a working site on day zero. Auth stays dark until you add your own Supabase keys — but nothing is broken while you decide.

I ran this before writing the slide, because a demo that needs configuration to survive isn't a demo, it's a rehearsal.

While it builds

What's actually guarding the thing you just forked

Seven checks block a merge

  • Unit tests · 4,750 of them
  • Accessibility · WCAG, real browser
  • E2E · chromium, firefox, webkit
  • RLS conformance · against a live database
  • Component structure · the 5-file pattern
  • Auth config drift · repo vs live project
  • Signup mailer · a real form, a real inbox

They run in parallel

So the wait is the slowest one, not the sum. Adding four checks this week cost zero extra minutes.

And they apply to me. There's no admin override — bypassing means editing the rule, which is a visible act instead of a click.

While it builds · the real lesson

Most of my bugs were green checks

Not failures. Successes that measured nothing.

A test asserting nothing

if (errorBanner.isVisible()) {
  expect(retryButton).toBeVisible();
}
// passes when the banner never appears

An account delete that deleted nothing

No delete policy on the table. The database filtered the request to zero rows and returned no error. The app said "permanently deleted" and signed you out.

While it builds · the fix

Count the assertions, not the checkmarks

[assertion-count] 4 of 17 passing test(s) ran ZERO assertions (#396):
  accessibility.spec.ts:23 › homepage passes automated checks
  cross-page-navigation.spec.ts:166 › external links open in new tab
  …

# nine of these across 24 shards and three browsers.
# now a merge-blocking gate, in the template you just forked.

One of those nine was hiding the delete bug. Nine tests, months of green, one real data-protection defect underneath.

What it costs you

The parts I'd want to know before forking

Real constraints

  • Static export — no server API routes in production
  • Server logic lives in Supabase or edge functions
  • Docker-first; local pnpm isn't supported
  • Opinionated: 5 files per component, one migration file

Who it suits

  • Small teams shipping client work
  • People who want the CI already argued about
  • Anyone tired of rebuilding auth for the fourth time
